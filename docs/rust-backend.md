# Rust-бэкенд: устройство и правила

Бэкенд — `crates/server/` (Cargo-workspace: корневой `Cargo.toml`, `crates/`, `xtask/`), около 4 700 строк: axum 0.7 + tokio, sqlx/PostgreSQL,
собственный WebSocket-игровой цикл. Здесь описано, как он разрезан на слои и что
можно менять, не ломая остальное.

## Слои

```
main.rs        сборка приложения: конфиг, пул БД, миграции, роутер, слушатель
config.rs      Figment: default.toml → BRAINSTORM_* env
db.rs          PgPool, миграции, health-запрос
error.rs       AppError → HTTP-статус + JSON { error: { code, message } }
middleware/    auth (сессия + роль), admin (только Role::Admin), cors, rate_limit
routes/        HTTP: auth, rooms, ai, leaderboard, profile, admin, health
ws/            игровой цикл: join, start, question, answer, power-up, cheat, game_over
services/      I/O и внешние системы: accounts, history, leaderboard, audit,
               questions, ai/{providers, router, cache}
domain/        чистые правила без I/O: room, player, power_up, mode, role, cheat
```

Правило зависимостей — только вниз: `routes`/`ws` → `services` → `domain`.
`domain` не знает про HTTP, БД и таймеры tokio; всё, что требует времени или
сети, живёт в `ws/` или `services/`.

## Домен

- `Room` — код, состояние (`Waiting → Starting → Playing → Finished`), настройки,
  игроки, вопросы, текущий вопрос, `question_token` и дедлайн.
- `Player` — счёт, серия, жизни, команда, рука усилений, `outbox` для приватных
  событий и `award(correct, mode, speed)`, который и начисляет очки.
- `GameMode` — все различия режимов ([game-modes.md](game-modes.md)).
- `PowerUp` — двойные очки, заморозка таймера, удаление двух вариантов.
- `Role` — `player`, `cheater`, `admin`. Роль живёт в `users.role` и попадает в
  `AuthContext` при каждом запросе, поэтому права проверяются на сервере, а не в
  интерфейсе.
- `CheatPowers` — приватный бюджет способностей читера (см. ниже).

`RoomSettings::clamp()` — единственное место, где настройки приводятся к
допустимому диапазону (5–30 вопросов, 2–6 вариантов, 10–120 с, тема ≤ 200
символов). Он же применяет принудительный таймер режима, поэтому клиент не может
обойти правило блица.

## Игровой цикл (`ws/`)

1. `join_room` — авторизация по cookie, поиск комнаты, посадка игрока.
   Повторный коннект с тем же аккаунтом переносит счёт, а не плодит дубль.
2. `start_game` — только хост. Генерация вопросов (с кэшем), рассадка команд,
   выдача жизней, `reset_for_new_game` для каждого игрока.
3. `question_emitted` — вопрос без правильного ответа и без чужих вариантов;
   дедлайн хранится на сервере, клиент получает `time_limit`.
4. `submit_answer` — принимается один раз, считается `speed` по дедлайну,
   начисляются очки, обновляется серия и жизни.
5. `reveal_and_advance` — идемпотентен по `question_token`: устаревший таймер
   или дублирующий вызов просто выходят. Здесь же решается, закончилась ли игра
   (кончились вопросы или все выбыли в `lives`).
6. `game_over` — итоговая таблица, счёт команд, `persisted`; запись в БД
   запускается отдельной задачей, чтобы не держать сокет.

Приватные события (рука усилений, скрытые варианты) уходят в `Player::outbox`
конкретному сокету; broadcast видят все, поэтому туда такие данные не попадают.

## Роли и режим читера

Регистрация принимает два кода вместо пароля: `1778` выдаёт роль `cheater`,
`19112009` — `admin`. Код проверяется на сервере в `routes/auth.rs`; обычный
пароль короче 12 символов отклоняется. Роль возвращается в `register`/`login`/
`me`, интерфейс только показывает бейдж и лишние ссылки.

`admin` открывает `/api/admin/*` (через `middleware/admin.rs`): статистику,
список пользователей, смену роли, сброс пароля, бан, закрытие комнат,
рассылку, переключение ИИ-провайдера, размер кэша вопросов и журнал аудита.
Отдельного «ключа активации» больше нет — права определяются только ролью в БД.

`cheater` садится в комнату как обычный игрок, но получает приватный набор
способностей, который сервер выдаёт заново каждую игру:

| Способность | Что делает | Использований |
|---|---|---|
| `peek` | присылает только этому игроку `cheat_reveal` с верным вариантом | 3 |
| `freeze` | +10 секунд к текущему вопросу для всех (`cheat_used`) | 2 |
| `steal` | переносит до 50 очков у лидера этому игроку (`cheat_used`) | 1 |
| `double` | удваивает очки следующего верного ответа (`cheat_armed`) | 2 |
| `mute` | жертва теряет голос в чате до конца игры (`muted`) | 2 |
| `jinx` | следующий верный ответ жертвы приносит 0 очков (`jinxed`) | 2 |
| `hijack` | жертва выбывает, её очки переходят читеру (`hijacked`) | 1 |
| `rewrite` | читер подменяет текущий вопрос своим (`question_emitted`, `source: "cheat"`) | 2 |

Бюджет хранится в `Player::cheat`, списывается на сервере и приходит клиенту
событием `cheat_state` после каждого применения — подделанный клиент не может
выдать себе лишние использования. Неудачная попытка (жертва не найдена, ход
недоступен) бюджет не тратит. `is_cheat` в `players_updated` не уходит:
остальные игроки не знают, кто читерит, — признаком служит приватный
`cheat_state`, который получает только читер.

Жертва выбирается по имени без учёта регистра; `mute`/`jinx`/`hijack`
адресные, `rewrite` — общий. Эффекты видны всем (`muted`, `hijacked` в
`players_updated`), но автор остаётся анонимным.

## Чат и эмодзи

Чат живёт в домене (`domain/chat.rs`), а не в сокете: `ChatLog` хранит последние
50 сообщений комнаты, проверяет длину (≤ 300 символов, обрезка пробелов),
запрещает пустые сообщения и ограничивает частоту — не чаще одного сообщения
в 400 мс с игрока. Причина отказа приходит адресно событием `error` с кодом
`chat_too_fast`, `chat_muted` или `chat_empty`.

| Сообщение клиента | Что происходит |
|---|---|
| `chat_send` `{text}` | `chat_message` всем: `{from, text, at}` |
| `emoji` `{emoji, target?}` | `emoji` всем: `{from, emoji, target}`; палитра фиксирована, чужой символ → `emoji_not_allowed` |

Эмодзи — это «бросок» в игрока: палитра (😂🔥😱👏💀🤡❤️🎯) задана на сервере,
поэтому клиент не может прислать произвольную картинку. Цель необязательна;
несуществующая цель игнорируется, чтобы бросок не срывался из-за опечатки.

Мьют из `CheatPowers::mute` действует на оба канала: замьюченный игрок получает
`chat_muted` и на текст, и на эмодзи.

## Переподключение

`ReconnectState` (см. `domain/player.rs`) переносит счёт, жизни, серию, руку
усилений, бюджет читера и наложенные эффекты (`muted`, `jinxed`, `hijacked`)
на новый сокет. Без этого перезагрузка страницы обнуляла бы читера и снимала
мьют, то есть была бы бесплатной отменой наказания.

## ИИ-провайдеры (`services/ai`)

`router.rs` держит список провайдеров в порядке приоритета и переключается на
следующий при ошибке или таймауте. Провайдеры — `providers/*`: `openai.rs`
обслуживает и OpenRouter (свой `base_url`), и OpenAI, рядом `gigachat.rs` и
`ollama.rs`; когда не ответил никто, `services/questions.rs` отдаёт офлайн-банк.
`cache.rs` кэширует наборы вопросов по
тема+сложность+количество, поэтому повторная игра по той же теме не тратит
токены. Без ключей работает офлайн-банк: приложение остаётся играбельным.

## Ошибки и наблюдаемость

- Любая ошибка возвращается как `{"error":{"code":"...","message":"..."}}`;
  `AppError` сам знает свой статус. Внутренние детали в ответ не попадают.
- Логи — `tracing` в JSON, фильтр `RUST_LOG`; в сообщениях есть латентность
  генерации, число вопросов, провайдер.
- `/health` — liveness, `/readyz` — проверка БД.
- `DATABASE_URL` подходит от Supabase как есть: TLS и режим пулера
  определяются по URL ([database/supabase.md](database/supabase.md)).

## Как расширять

| Задача | Куда идти |
|---|---|
| Новый режим | `domain/mode.rs` + подписи в UI ([game-modes.md](game-modes.md)) |
| Новый эндпоинт | `routes/<тема>.rs`, регистрация в `routes/mod.rs` |
| Новое WS-сообщение | ветка в `ws/mod.rs`, событие для клиента, тест в `#[cfg(test)]` |
| Новый ИИ-провайдер | `services/ai/providers/`, регистрация в `router.rs` |
| Новое поле в БД | `migrations/`, затем `services/*` и `db.rs` |

## Правила, которые нельзя нарушать

1. `unwrap()` в продакшен-коде запрещён: `?`, `expect("причина")` или `AppError`.
2. Изменение правил игры — только через `domain`, не в обработчике сообщения.
3. В broadcast не должно быть приватных данных.
4. Новое поведение — новый тест в том же файле; тесты с живой БД помечаются
   `#[ignore]`.
5. `make agent-verify` (fmt → check → clippy `-D warnings` → test) должен быть
   зелёным до того, как задача считается сделанной.

## Проверено

`cargo test` — 40 тестов (правила режимов и очков, усиления, способности
читера, добивание набора вопросов до запрошенного числа, идемпотентность
раскрытия вопроса). `scripts/e2e-modes.py` прогоняет живые партии через HTTP и
WebSocket. Роли, админ-API и способности читера проверены живыми запросами:
регистрация по кодам, `403` для не-админа, полный набор из четырёх способностей
в партии, выбывание за ошибку в `sudden` и 30 вопросов в `marathon`.
